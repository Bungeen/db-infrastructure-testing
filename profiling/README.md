# Гипотезы деградации:

Общая деградация превышает 30% для p95 по всем запросам. Это связано в первую очередь с ростом количества данных.

Особый рост замечен за
1. **/olap/stats**
Гипотеза: Запрос содержит несколько тяжёлых JOIN, которые раскрываются (см. olap_stats.txt) в последовательное (Seq Scan) вложенное чтение по миллиону данных. Дополнительно, одна из миграций создаёт дополнительную таблицу соизмеримую с самой быстрорастущей - расходы. Как минимум необходима индексация с новой таблицей

2. **/olap/trend**
Гипотеза: Рост количества данных в таблице привёл к падению скорости агрегации и сортировки данных в ней. Необходима индексация по дате (date) для данного End-point'а с целью ускорения группировки по месяцам

3. **/oltp/expense**
Гипотеза: Добавление нового поля для пользователя, которое денормализует БД и требует постоянного обновления, вызывает блокировки строки у пользователя на запись, что при высокой нагрузке начнёт создавать очереди.

4. **остальные**
Гипотеза: произошёл многократный рост объёма данных, а в тестировании участвовали крайне тяжёлые запросы, что создают блокировки при работе с разнообразными данными на протяжении длительного времени.

Дорогая операция `Hash Join` | Добавление индекса `Hash` на подкатегории, которых больше всего (нет необходимости сравнивать подкатегории). <br> Добавление индекса `BTree` на таблицу `expense_approvals` по статусу. <br> Добавление индекса `BTree` на таблицу `expense_transactions` по `date`. Не используем `BRIN`, т.к. по бизнес правилам данное поле заполняется пользователем, т.е. данные по нему не отсортированы в БД. <br> `Materialized View` для предварительного расчета. <br> `UNIQUE BTree` индекс на `Materialized View` позволяет использовать `REFRESH MATERIALIZED VIEW CONCURRENTLY`, что позволяет не блокировать таблицу при чтении/записи при пересчёте. | Индексы ускорят само выполнение запроса, но не исправят проблему целиком (останется 4 JOIN операции). <br> `Materialized View` будет решать оставшуюся проблему, при этом сам будет рассчитываться быстрее за счёт индексов |

Существенное ускорение за счёт предварительного расчёта |

# Выводы
Анализируя `EXPLAIN`, можно сделать вывод, что не всегда применяются новые индексы, т.к. планировщик не всегда считает их использование уместным. При этом часть планов стремительно уменьшилась (относится к EndPoint'ам с MV), а другие стали использовать индексы.

Общая нагрузка системы стала существенно ниже. Задержки на запросах допустимы в рамках текущей бизнес проблемы.

Самым долгим запросом оказалась вставка Расхода, при этом его выполнение по `p95` около `110ms`, что допустимо для пользователя, который в ручном порядке вводит данные. Остальные EndPoints оказались быстрее.
